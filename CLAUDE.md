# CLAUDE.md

## Working in this repo

- Default to no code comments; add terse one-liners only when the WHY (not the WHAT) is non-obvious from the code.
- Do NOT bandaid over upstream bugs or platform gaps in any dependency — raise them immediately with a severity (critical / high / medium / low).

## Platform shortcomings

Known gaps this module cannot fix on its own. Do not paper over them — reference this section when you hit them and, if new ones surface, add them here.

- **`motion.Move` ignores per-pose `vel_degs_per_sec` / `acc_degs_per_sec2`** (medium). The pose-switcher's `set_position_by_name` goes through `motion.Move`, which has no first-class vel/acc fields and whose builtin planner ignores arbitrary `Extra` keys. The bartender's own flow dodges this by calling `armplanning.PlanMotion` + `arm.MoveThroughJointPositions` with explicit `arm.MoveOptions`, so configured per-pose speeds only apply there. Anything that drives a pose through `motion.Move` (app.viam.com's set-pose button, Stream Deck, direct `set_position_by_name` DoCommand) runs at the arm's default speed. Fix would require routing the pose-switcher around `motion.Move` to match the bartender's path.
- **rdk places a code-built static frame's geometry at its parent, not at the frame's pose** (high). In rdk v1.17.0, `referenceframe.NewStaticFrameWithGeometry(name, pose, geom)` keeps `pose` for transforms but `FrameSystemGeometries` (and so the planner) puts `geom` relative to the frame's *parent*, ignoring `pose`. Only frames loaded from config get wrapped so their geometry follows the pose. The docstring doesn't say this, so the obstacle silently lands somewhere else. The parked bottle hit on 2026-11-19 happened this way: the parked-bottle capsule sat at the world origin inside the arm base, and the planner carried the back bottle through the real parked bottle. Until upstream fixes or documents this, build these frames with a zero frame pose and put the whole placement in the geometry's own pose.
- **Orientation constraints on joint-space goals bound the arm's own frame, not the held object** (high). For a goal given as joint positions, `armplanning` (`planToDirectJoints`) turns every frame into a goal pose, then drops any frame the goal names with unchanged inputs as "pinned". Static frames riding on the arm, like the held object, always look unchanged, so a no-spill constraint bounds the arm's own frame instead, which is wrong both ways. `IgnoreTheta` on the arm's frame frees the wrist roll that tips a shaker gripped from the side, so before 2026-11-19 the carry to the joint-space `cleaner-hover` could roll the shaker upside down. And the arm's frame often has to turn where the shaker doesn't: leaving the held object out of the goal (RDK supports partial goal configurations, RSDK-14556) brought the shaker back under the constraint but kept the arm's frame there too, and the serve → `cleaner-hover` carry became unplannable, because the gripper turns to face the other way while the shaker stays upright. There is no way to name the frame a constraint applies to. `moveToJoints` works around it for level carries by planning first to the held object's pose at the goal joints, where only the held object is constrained, then to the joints themselves. `TestCarryToJointPoseKeepsASideHeldObjectLevel` and `TestCarryFromServeApproachToCleanerHover` fail if RDK changes this.
- **Linear-move failures don't say why** (low). `armplanning` returns `linear with cbirrt not allowed and no direct solutions found` whether the line is blocked by an obstacle or by a joint limit. A pose given in space lets IK land in any equivalent configuration (wrist flipped, J6 a full turn away), so a straight move that follows can need a joint past its limit. The stir insert failed this way on 2026-11-18: the carry to `stir-hover` arrived with J6 at -336.9° and the insert needed -361.4° (limit ±360°). When a straight move follows a carry, teach the pose before it as `joint_positions_degs` so the arm always arrives in the same configuration.
